# FORMAL-DOC-009 — Document delivery lifecycle and freshness projection

Status: `FORMAL-DOC-009 validation candidate`

## Scope

This gate materializes the delivery lifecycle already reserved by the Stage-5 formal-document authority without changing Stage-4 or Stage-5 migration identities.

Implemented runtime:

- reusable current-source freshness projection for both formal document types,
- append-only lifecycle event history,
- paper `printed` events,
- paper `signed_scan_attached` events,
- electronic `electronic_presented` events,
- tenant- and student-scoped delivery authorization,
- idempotent delivery commands,
- safe delivery audit/outbox evidence.

No new migration is introduced.

## Freshness projection

Freshness is derived from canonical source data, not from a mutable document status column.

For each document type:

- rebuild canonical evidence from the same sources used by preview/approval,
- calculate the current evidence bundle SHA-256,
- resolve the latest approved immutable revision,
- return `fresh` only when the latest revision evidence hash equals the current evidence hash,
- otherwise return `regeneration_required`.

Reading freshness has no business side effects. In particular it does **not** emit `regeneration_detected` events merely because the projection is stale. That event type remains reserved for a future explicit event-producing source-change workflow rather than being generated by GET requests.

## Delivery lifecycle

Delivery records are append-only `formal_training_document_events` rows. The canonical `formal_training_documents` revision and its canonical PDF asset are never rewritten.

### Paper mode

Allowed:

- `printed`,
- `signed_scan_attached`.

A reprint is another delivery fact for the same immutable revision; it does not create a new business revision.

`signed_scan_attached` requires an existing:

- same-tenant `file_assets` row,
- status `ready`,
- purpose `formal_training_signed_scan`,
- non-deleted asset,
- verified SHA-256.

Gate 9 does not fabricate upload transport. The existing canonical Uploads/Assets capability remains responsible for creating such a ready asset when that runtime is materialized.

### Electronic mode

Allowed:

- `electronic_presented`.

It does not accept a signed-scan asset and it does not claim that authenticated approval or presentation is a qualified electronic signature, XAdES, or any other specific statutory electronic-signature mechanism.

## API

Gate 9 adds:

- `GET /course-enrollments/{courseEnrollmentId}/formal-documents/freshness`,
- `GET /formal-training-documents/{documentId}/events`,
- `POST /formal-training-documents/{documentId}/delivery-events`.

The delivery command requires UUID `Idempotency-Key`.

The canonical API inventory becomes:

- **187 HTTP requirement rows**,
- **173 unique OpenAPI path/method operations**,
- **14 shared operation aliases**.

## Permission boundary

New permission:

`formal_documents.deliver`

Scope:

`student_scoped`

Owner and OfficeAdmin receive it through the canonical courses/training group. Instructor receives it only as a conditional permission. Lecturer remains view/download only unless explicitly granted according to the RBAC authority.

## Audit privacy

Delivery writes:

`formal_document.delivery_recorded`

Audit/outbox carries only delivery state/event type metadata. The signed-scan bytes, canonical PDF bytes, evidence bundle, PESEL and PKK are not copied into audit/outbox.

## Runtime proof required

FORMAL-DOC-009 must prove:

1. freshness is `fresh` only for an exact current evidence hash,
2. source drift changes freshness to `regeneration_required`,
3. freshness reads do not write `regeneration_detected` or any other lifecycle event,
4. paper print is append-only and idempotent by Idempotency-Key,
5. signed scan requires same-tenant, ready, purpose-bound, SHA-256 verified asset,
6. paper mode rejects `electronic_presented`,
7. electronic mode accepts `electronic_presented`,
8. electronic mode rejects paper print and signed-scan attachment,
9. lifecycle history remains readable in append-only order,
10. delivery never rewrites canonical document bytes/hash or creates a fake document revision,
11. cross-tenant freshness/event/delivery routes fail closed,
12. audit/outbox delivery evidence is written without raw document or evidence payload,
13. API contract is complete at 187/173,
14. Stage-4 authority remains 170/112/112,
15. Stage-5 formal-document migration authority remains 11 steps with unchanged execution identity,
16. PKK provider runtime remains frozen.

## Explicitly out of scope

- upload presign/complete runtime,
- statutory electronic-signature mechanism,
- direct PDF editing,
- deletion or replacement of prior formal-document revisions,
- mutating PKK operations,
- automatic side-effecting `regeneration_detected` on GET freshness.
